## 2. Two shapes for the habit data

### Shape A — one log object per habit per day (rejected)

```ts
interface DayLog { mark?: 't' | 'x'; reason?: string; urges?: number; slips?: number; value?: number }
interface Habit { id; name; kind; …; days: Record<DayKey, DayLog> }   // sync key: day:<id>:<day>
```

- 2.0 marks live in `mark:` keys. Shape A needs either a second home for marks (two owners) or a migration that rewrites every `mark:` key (not additive, breaks plan section 7).
- Last-write-wins works per key. A reason typed on one phone and an urge added on another phone on the same day would collide; one is lost.

### Shape B — one map per fact (chosen)

Each fact has its own map on the habit and its own sync prefix. One owner per fact, one merge unit per fact, and 2.0 marks are untouched.

```ts
// src/domain/types.ts
export type DayKey = string                       // 'YYYY-MM-DD', local time
export type Mark = 't' | 'x'
export type WeekStart = 0 | 1 | 2 | 3 | 4 | 5 | 6  // 0 = Sunday (default)

interface HabitBase {
  id: string
  name: string
  later?: boolean                                 // paused (R-K8)
  timerMin?: number                               // default 5 (build) / 20 (reduce)
}
export type Habit =
  | HabitBase & { kind: 'daily';  marks: Record<DayKey, Mark>; reasons?: Record<DayKey, string> }
  | HabitBase & { kind: 'weekly'; goal: number;   marks: Record<DayKey, Mark>; reasons?: Record<DayKey, string> }
  | HabitBase & { kind: 'reduce'; budget?: number; replacement?: string; urges: Record<DayKey, number>; slips?: Record<DayKey, number> }
  | HabitBase & { kind: 'number'; target?: number; unit?: string; values: Record<DayKey, number> }

export interface AvoidItem { id: string; name: string; replacement: string }

export interface Settings {
  weekStart: WeekStart       // synced
  missRules: boolean         // synced, default true (R-M4)
}

export interface Doc {
  habits: Habit[]
  avoid: AvoidItem[]
  notes: Record<DayKey, string>
  settings: Settings
  cur: string                // device-local UI state
  theme: 'light' | 'dark'    // device-local, as in 2.0
}
```

### Sync records (additive)

| Key | Value | New? |
|---|---|---|
| `habit:<id>` | `{name, order, kind?, goal?, budget?, target?, unit?, timerMin?, replacement?, later?}` | extended |
| `mark:<id>:<day>` | `'t' \| 'x'` | unchanged |
| `note:<day>` | string | unchanged |
| `reason:<id>:<day>` | string | new |
| `urge:<id>:<day>` | integer ≥ 1 | new |
| `slip:<id>:<day>` | integer ≥ 1 | new |
| `val:<id>:<day>` | number | new |
| `avoid:<id>` | `{name, replacement, order}` | new |
| `set:<name>` | JSON value (`weekStart`, `missRules`) | new |

A missing `kind` reads as `'daily'` (R-K7). Zero counts are stored as a deleted record, not as `0`.

## 3. Rules that settle edge cases

These are decisions made in phase 3 from the spec. Overrule any of them before phase 4.

| # | Case | Decision |
|---|---|---|
| E1 | Kind change after creation | Daily ↔ Weekly allowed (same marks). Reduce and Number are fixed; to change, make a new habit. No data is reinterpreted. |
| E2 | Reason when the mark leaves `x` | The reason is kept but hidden. It shows again if the day goes back to `x`. Review and two-miss read reasons only for `x` days. |
| E3 | Timer ends after midnight | Settles on the day the timer **started**. |
| E4 | Build timer ends and the day is already `t` | No change. If the day is `x`, it becomes `t` (reason kept hidden, E2). |
| E5 | Timer for a habit that is deleted or moved to Later before it settles | Dropped, nothing logged. Starting a timer on a Later habit is not offered. |
| E6 | Two-miss check trigger | Shown once, right after the user marks the second consecutive `x` for a Build daily habit. Consecutive = calendar days D-1 and D. A blank between two `x` breaks "in a row". |
| E7 | Restart prompt | Shown on day D for habit H when H is Build daily, D-1 is `x` and D is blank. Derived state, nothing stored; disappears once D is marked. |
| E8 | Review card dismissal | Stored per device (`streakcal.ui`, key = week's first day). Not synced. |
| E9 | Week start change | All weekly numbers are recomputed (ADR 0003). Nothing is migrated. |
| E10 | Slip without a budget | Not possible. Removing a budget hides existing slips; they are kept and show again if a budget is set. |
| E11 | Score on a day with no active Build daily habits | No score shown (not "0 / 0"). |
| E12 | Week streak when the current week is incomplete | The current week counts if its goal is already met; otherwise it is skipped, not a break (R-P5). |

## 4. Domain module (pure, no DOM, no Capacitor)

One owner per rule. The UI, the store, the widget payload and the tests call these; nothing else computes a total, streak or score.

```ts
// src/domain/week.ts
export function weekOf(day: DayKey, ws: WeekStart): DayKey            // first day of that week
export function weekDays(first: DayKey): DayKey[]                     // 7 keys
export function lastWeeks(today: DayKey, ws: WeekStart, n: number): DayKey[]  // n week starts, oldest first

// src/domain/progress.ts
export interface Week { first: DayKey; amount: number; of?: number; met: boolean | null }  // met null = no goal/budget
export function total(h: Habit, today: DayKey): number
export function thisWeek(h: Habit, today: DayKey, ws: WeekStart): Week
export function trend(h: Habit, today: DayKey, ws: WeekStart, n = 8): Week[]
export function streak(h: Habit, today: DayKey, ws: WeekStart): { cur: number; best: number; unit: 'day' | 'week' } | null
//  daily → existing 2.0 rule (only x breaks); weekly → weeks with goal met; reduce+budget → weeks within budget; else null

// src/domain/score.ts
export function dailyScore(doc: Doc, day: DayKey): { done: number; of: number } | null   // null when of = 0 (E11)

// src/domain/rules.ts
export type Prompt = { kind: 'restart'; habit: string } | { kind: 'twoMiss'; habit: string; reasons: [string?, string?] }
export function restartPrompts(doc: Doc, today: DayKey): Prompt[]                  // E7
export function twoMissAfter(doc: Doc, habitId: string, day: DayKey): Prompt | null  // E6, called on mark change

// src/domain/review.ts
export interface ReviewRow { habit: string; kind: Habit['kind']; week: Week; reasons: { day: DayKey; text: string }[] }
export function isReviewDay(today: DayKey, ws: WeekStart): boolean                // last day of the week
export function weekReview(doc: Doc, today: DayKey): ReviewRow[]

// src/domain/actions.ts  — every change to the doc goes through here (pure: Doc in, Doc out)
export function setMark(doc: Doc, id: string, day: DayKey, m: Mark | null): Doc
export function setReason(doc: Doc, id: string, day: DayKey, text: string): Doc
export function addUrge(doc: Doc, id: string, day: DayKey, delta: 1 | -1): Doc
export function addSlip(doc: Doc, id: string, day: DayKey, delta: 1 | -1): Doc
export function setValue(doc: Doc, id: string, day: DayKey, v: number | null): Doc
export function upsertHabit(doc: Doc, h: Habit): Doc      // enforces E1
export function setLater(doc: Doc, id: string, later: boolean): Doc
export function upsertAvoid(doc: Doc, a: AvoidItem): Doc
export function setSettings(doc: Doc, s: Partial<Settings>): Doc

// src/domain/timer.ts
export interface Timer { habitId: string; kind: 'start' | 'delay'; startedAt: number; endsAt: number }
export function settle(doc: Doc, t: Timer, now: number): Doc   // E3–E5; returns doc unchanged if now < endsAt

// src/domain/records.ts   (moved from store.ts)
export const PROTOCOL = 3
export function flatten(d: Doc): Record<string, unknown>
export function rebuild(flat: Record<string, unknown>, prev: Doc): Doc
export function normalize(raw: unknown): Doc               // loadDoc: 1.0, 2.0, 3.1 → Doc; never throws
```

Existing files: `calendar.ts` moves to `src/domain/calendar.ts` unchanged; `streaks.ts` keeps `isMs`, `nextMs`, `peaks` and its day-streak function becomes the `daily` branch of `streak()`.

## 5. Platform layer

```ts
// src/platform/timerPort.ts   (ADR 0001)
export interface TimerPort {
  current(): Promise<Timer | null>
  start(t: Omit<Timer, 'startedAt' | 'endsAt'> & { minutes: number }): Promise<Timer>   // rejects 'busy' if one runs (R-T3)
  cancel(): Promise<void>                                                              // stop early: nothing counted (R-T2)
  drain(): Promise<Timer[]>                       // finished, not yet settled; removes them
  permission(): Promise<'granted' | 'denied' | 'prompt'>
  onChange(cb: () => void): () => void
}
export const timerPort: TimerPort   // NativeTimerPort on Android, WebTimerPort (localStorage 'streakcal.timer') elsewhere
```

App start and every `visibilitychange → visible`: `for (t of await timerPort.drain()) doc = settle(doc, t, Date.now())`, then one `store.commit(doc)`.

`src/lib/store.ts` keeps only the sync engine and persistence; it imports `flatten`/`rebuild`/`normalize` from the domain. It sends `{v: 3, since, changes}` and reads `GET /api/health → {ok, protocol}` before the first push (ADR 0002).

`src/lib/widgetPayload.ts` → payload v3:

```json
{ "v": 3, "theme": "light", "weekStart": 0, "missRules": true,
  "habits": [{ "id": "h1", "name": "Read", "kind": "daily", "later": false, "timerMin": 5,
               "marks": {}, "urges": {}, "slips": {}, "values": {}, "goal": null, "budget": null, "target": null }],
  "hol": {} }
```

## 6. UI module split

`App.tsx` becomes a thin shell that holds `doc` and routes. Screens follow the phase 2 canvas:

```
src/ui/
  App.tsx            shell: doc state, store wiring, timer drain, route
  Home.tsx           calendar grid, badge (total big, streak small), daily score, restart prompts, review card
  DaySheet.tsx       per-habit row by kind: tick/x + reason (build), urges/slips (reduce), value (number)
  TwoMissSheet.tsx   two reasons side by side; Change / Smaller → HabitEdit; Keep → close
  HabitsSheet.tsx    active list, Later section, Avoid section, + New habit
  HabitEdit.tsx      kind picker ("Break a habit" label for reduce), goal/budget/target, timer length, replacement
  Detail.tsx         total, this week, streak, 8-week trend, start timer, move to Later
  TimerScreen.tsx    countdown from endsAt, replacement action, stop; permission hint (R-T5)
  ReviewCard.tsx     weekReview rows, reasons raw, dismiss
  Settings.tsx       week start, miss rules, sync, backup, theme
  skin.css           Glass Bento tokens (Roboto, one --done green in both modes, miss grey)
```

Screens call `actions.*` and `progress.*` only; they never touch `marks` maps directly.

## 7. Native (Android)

### Shape choice for widget rules

- **A — Java recomputes from day data (chosen).** The widget must roll over at midnight and show a settled timer without the app running; only native code is awake then. Kept honest by **shared fixtures**: `tests/fixtures/rules/*.json` (input doc + today + expected totals/streaks/score) run by `node --test` against `progress.ts` and by JUnit against `WidgetData.java`.
- **B — web precomputes a view model.** Rejected: stale after midnight and after a timer ends.

### New and changed classes

```
WidgetData.java          + kind, goal/budget/target, urges/slips/values maps, weekStart
                         + total(h, today), thisWeek(h, today), dayStreak/weekStreak, dailyScore(today)
                         + overlay(List<Timer> finished)   // same settle rule as timer.ts
TimerStore.java          SharedPreferences "timer": current {habitId, kind, startedAt, endsAt}; finished[] list
                         start() / cancel() / finishDue(now) / drain()   — pure logic, JVM-testable
TimerBridgePlugin.java   @CapacitorPlugin("TimerBridge"): current, start, cancel, drain, permission, requestPermission
TimerNotifier.java       ongoing notification with countdown chronometer (setChronometerCountDown) + Stop action;
                         "done" notification on end; channel "timer"
TimerAlarmReceiver.java  inexact AlarmManager at endsAt → finishDue(), "done" notification, refresh widgets
TimerActionReceiver.java widget "Start" / notification "Stop" broadcasts
TimerConflictActivity    translucent dialog "Cancel the running timer?" when a widget start meets a running timer (R-T3)
ActionWidgetProvider     widget 2 (R-G2): selected habit, total, this week, Start/Delay button → TimerActionReceiver
                         reuses WidgetSettingsActivity's habit picker
StreakWidgetProvider     widget 1 (R-G1): grey miss, total on badge, "Today x / N", grid follows weekStart
```

Manifest: `POST_NOTIFICATIONS` (asked at first timer start), two receivers, the conflict activity, the action widget provider. No exact-alarm permission.

### Beta flavor (R-S4)

`productFlavors { prod {}; beta { applicationIdSuffix ".beta"; resValue "string", "app_name", "Streak Calendar Beta" } }`. Own app id → own WebView storage → own data. Beta sync points at its own server or database file (ADR 0002). Version `3.1.0` / `versionCode 30100`.

## 8. Data flow summary

```
user tap ─▶ actions.* (pure) ─▶ store.commit(doc) ─▶ localStorage + dirty records ─▶ sync (v3)
                                     └──────────────▶ widgetPayload v3 ─▶ WidgetBridge ─▶ widgets
widget Start ─▶ TimerActionReceiver ─▶ TimerStore (native owns) ─▶ notification + alarm
alarm / app open ─▶ TimerStore.finishDue ─▶ finished[] ─▶ widget overlay   |   app: drain() ─▶ settle() ─▶ commit
```
